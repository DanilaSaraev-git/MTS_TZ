# Конституция Review Platform

## Основные принципы

### I. Сначала контракт

Публичные границы ДОЛЖНЫ быть спроектированы и проверены до зависящей от них реализации.

- `contracts/review-platform/v1/openapi.yaml` является каноническим контрактом между React web и backend.
- JSON Schema в `contracts/review-platform/v1/schemas/` являются каноническими контрактами между engine и skill.
- Web ДОЛЖЕН генерировать транспортные типы из OpenAPI и НЕ ДОЛЖЕН содержать рукописные копии серверных DTO.
- Экспорт FastAPI ДОЛЖЕН оставаться семантически совместимым с каноническим OpenAPI.
- Изменение контракта ДОЛЖНО обновлять затронутые схемы, примеры и `CHANGELOG.md` в одном контрактном PR.
- Удаление поля, добавление обязательного поля или изменение существующей семантики ДОЛЖНО создавать новую основную версию контракта.

Обоснование: web и backend/skills разрабатываются параллельно и требуют одного независимого от языка источника истины.

### II. Одно доменное ядро и явные адаптеры

Семантика ревью ДОЛЖНА иметь одну реализацию, независимую от канала поставки и инфраструктуры.

- `review-core` ДОЛЖЕН предоставлять крупные прикладные операции для документов, запусков, отчётов, диалогов и решений человека.
- Доменные и прикладные модули НЕ ДОЛЖНЫ импортировать FastAPI, SQLAlchemy, библиотеки очередей или SDK поставщиков моделей.
- React обращается к ядру через HTTP; API, worker и CLI являются точками сборки и адаптерами.
- Локальные CLI и AI skills ДОЛЖНЫ вызывать Python application/core напрямую и НЕ ДОЛЖНЫ требовать HTTP-сервер.
- Parser, repository, artifact storage, job queue, model и skill runtime ДОЛЖНЫ находиться за явными портами, если запланировано более одной реальной реализации.
- Новый сетевой сервис ДОЛЖЕН быть обоснован измеренным ограничением масштабирования, изоляции отказов или независимого развёртывания.

Обоснование: единое глубокое ядро не позволяет PoC, самостоятельному движку и web-сервису превратиться в три разных продукта.

### III. Неизменяемые свидетельства и изменяемое состояние рассмотрения

Входные данные и опубликованный результат модели ДОЛЖНЫ оставаться воспроизводимыми, а состояние человеческого рассмотрения ДОЛЖНО храниться отдельно.

- Версии документов и профилей проверки, execution snapshots, отчёты, замечания, evidence anchors и coverage НЕ ДОЛЖНЫ изменяться после публикации.
- Запуск ДОЛЖЕН ссылаться на точные версии и digests документа, контекста, профиля, skill, model profile, dialogue policy и engine.
- Диалог, proposed resolution и `HumanDecision` ДОЛЖНЫ храниться отдельно от неизменяемого отчёта.
- Изменяемые записи диалога и решения ДОЛЖНЫ использовать `expected_revision`; устаревшая запись ДОЛЖНА возвращать конфликт, а не молча перезаписывать состояние.
- Результат модели НЕ ДОЛЖЕН автоматически подтверждать, отклонять или изменять замечание либо исходный документ.
- Замечание остаётся кандидатом на проблему, пока решение человека не сохранено явно.

Обоснование: аналитик должен различать исходные свидетельства, результат модели и решение человека.

### IV. Валидация и тесты являются условиями выпуска

Результат или интеграция не считаются завершёнными, пока не проверены их границы и семантические инварианты.

- Результат engine ДОЛЖЕН пройти JSON Schema и семантические проверки до публикации отчёта.
- Семантические проверки ДОЛЖНЫ охватывать ID ссылок, точные цитаты и offsets, anchors, область отсутствующего требования и полное разбиение coverage.
- Большие документы НЕ ДОЛЖНЫ молча обрезаться. Частичная обработка ДОЛЖНА публиковать явные gaps источников или фрагментов; недоступный основной документ ДОЛЖЕН завершать запуск ошибкой.
- Каждый контрактный baseline ДОЛЖЕН проходить проверку OpenAPI, всех HTTP-примеров и всех skill-примеров.
- Изменения backend ДОЛЖНЫ проходить unit, contract и PostgreSQL integration tests; изменения web ДОЛЖНЫ проходить typecheck, component tests и применимый Playwright-сценарий.
- Синтетический сквозной сценарий ДОЛЖЕН работать через MSW, реальный HTTP adapter и локальный CLI/skill без расходящихся DTO.
- Регрессионные тесты существующего feature-001 PoC ДОЛЖНЫ оставаться зелёными.

Обоснование: синтаксически корректного JSON от модели недостаточно для ревью с проверяемыми ссылками на источники.

### V. Контроль объёма и разделение данных

Реализация ДОЛЖНА оставаться в пределах утверждённого среза и сохранять различие между свидетельствами и предположениями.

- Спецификация, план или список задач сами по себе не разрешают реализацию; реализация начинается только после явного поручения пользователя.
- Документы, правила, интервью, примеры и ограничения MTS ДОЛЖНЫ оставаться в `MTS/` и НЕ ДОЛЖНЫ попадать в общие skills, contracts или синтетические fixtures.
- Общие выводы ДОЛЖНЫ храниться в `knowledge/` с источниками и границами применимости.
- Текст документов, контекст и сообщения пользователя ДОЛЖНЫ считаться недоверенными данными, а не инструкциями, способными изменить правила engine или skill.
- Учётные данные поставщиков ДОЛЖНЫ оставаться на сервере и НЕ ДОЛЖНЫ попадать в browser payloads, public DTO, skills, reports, fixtures или безопасные logs.
- RAG, обучение, OCR, автономный выбор инструментов, автоматическое изменение документов и новая инфраструктура НЕ ДОЛЖНЫ добавляться без отдельно утверждённого требования.

Обоснование: продукт ещё проходит проверку, поэтому скрытое расширение объёма и утечка клиентской специфики создают больше риска, чем ценности.

## Ограничения стека и развёртывания

Ниже указан baseline реализации, проверенный 2026-09-04. Прямые зависимости ДОЛЖНЫ быть зафиксированы в lock-файлах. Изменение версии ДОЛЖНО выполняться отдельным PR и проходить проверки контрактов, миграций и регрессии. Если архитектура и публичные контракты не меняются, поправка конституции не требуется.

| --- | --- |
| Среда web | Node.js 24.20.0 LTS; npm 12.0.2 |
| Web-приложение | React/react-dom 19.2.8; TypeScript 6.0.3; Vite 8.2.2; plugin-react 6.1.1 |
| Данные и маршруты web | React Router 7.18.3; TanStack Query 5.102.8 |
| Контракты и тесты web | Orval 8.28.1; MSW 2.15.0; Vitest; Testing Library; Playwright |
| Интерфейс web | Tailwind CSS 4; доступные Radix UI primitives; React Hook Form; Zod; PDF.js |
| Среда Python | Python 3.14.7; uv 0.12.9 с закоммиченным `uv.lock` |
| Backend | FastAPI 0.141.1; Pydantic 2.13.5; pydantic-settings 2.15.0; Uvicorn 0.52.4 |
| Хранение состояния | PostgreSQL 18.6; SQLAlchemy 2.0.52 async; Alembic 1.19.1; psycopg 3.3.5 |
| Фоновые задания | Procrastinate 3.9.0 за портом `JobQueue`; transactional outbox; at-least-once delivery; idempotent handlers |

| Поставка | Docker Compose с reverse proxy, React SPA, API, worker и PostgreSQL |

Дополнительные ограничения:

- Первый HTTP v1 deployment ДОЛЖЕН содержать ровно одного настроенного оператором actor, одну organization и один workspace.
- HTTP v1 НЕ ДОЛЖЕН реализовывать login, accounts, membership, access roles, permission checks, cookie или bearer sessions, CSRF либо RLS как access control.
- `organization_id` и `workspace_id` являются пространствами имён данных и будущими миграционными швами, а не заявлением о текущей multi-organization isolation.
- Любой caller, достигший HTTP v1, действует как настроенный actor; API и reverse proxy ДОЛЖНЫ работать только внутри доверенного сетевого контура.
- Authentication, authorization, публичный доступ и multi-organization runtime требуют новой спецификации, threat model и ADR.
- React SPA и `/api` ДОЛЖНЫ использовать один origin в первом deployment.
- Первая система ДОЛЖНА оставаться модульным монолитом с отдельными процессами API и worker из одной Python codebase.
- PostgreSQL является источником истины для runtime metadata и изменяемого состояния. Байты артефактов ДОЛЖНЫ храниться через `ArtifactStore`.
- Procrastinate ДОЛЖЕН оставаться заменяемым за портом `JobQueue`; business state и outbox ДОЛЖНЫ фиксироваться атомарно.
- MinIO Community НЕ ДОЛЖЕН быть production dependency. Выбранный оператором S3-compatible service МОЖЕТ реализовывать optional adapter.
- LangChain, Redis, RabbitMQ, Kubernetes, vector database и managed cloud control plane находятся вне текущего baseline.

## Процесс разработки и критерии качества

1. Реализационные ветки ДОЛЖНЫ создаваться от текущего неизменяемого contract tag, указанного в `architecture/parallel-development.md`.
2. Web владеет `apps/web/`; backend/skills владеют `apps/api/`, `apps/worker/`, `apps/cli/`, `packages/`, `skills/` и `deploy/`. Изменения в `contracts/` требуют совместного review.
3. Fixture-based сквозной сценарий ДОЛЖЕН быть реализован до PostgreSQL, реальной очереди или реального model adapter: bootstrap → upload → create/poll run → immutable report → finding state → один dialogue turn → human decision.
4. Durable persistence и worker processing ДОЛЖНЫ реализовываться только после прохождения того же HTTP-сценария на deterministic fakes.
5. PR, изменяющий публичный HTTP или skill schema, ДОЛЖЕН быть слит до зависящих от него PR реализации web или backend.
6. CI ДОЛЖЕН завершаться ошибкой при несовместимости contracts/schemas/examples, расхождении generated web client, падении Python или TypeScript tests, регрессии PoC, утечке клиентских данных или provider secrets.
7. Review ДОЛЖНО подтверждать, что в текущий срез не попали auth runtime, multi-organization claims или клиентские материалы.
8. Зелёные технические тесты подтверждают только согласованность реализации и НЕ ДОЛЖНЫ фиксироваться как доказательство продуктовой ценности, спроса, экономии времени или успеха пилота.

Детали разработки и порядок задач находятся в `specs/002-target-review-platform/`. Правила продукта и ведения базы знаний остаются в `AGENTS.md`; `AGENTS.md` не заменяет инженерные принципы этой конституции.

## Управление конституцией

Эта конституция регулирует технические планы, генерацию задач, реализацию и review Review Platform. При противоречии с другим документом проекта действует конституция, если более позднее явное решение пользователя не требует поправки. Прямые поручения пользователя и системные инструкции остаются приоритетными.

- Поправки ДОЛЖНЫ вноситься через процесс Spec Kit constitution и содержать отчёт о влиянии синхронизации.
- Удаление существенного принципа или несовместимое изменение его смысла требует повышения MAJOR-версии.
- Новый принцип или существенное расширение governance требует повышения MINOR-версии.
- Уточнение без изменения обязательств требует повышения PATCH-версии.
- Каждая поправка ДОЛЖНА фиксировать дату ISO, обоснование и затронутые планы, контракты или миграционные работы.
- Каждый implementation plan ДОЛЖЕН включать Constitution Check до генерации задач.
- Каждый release или integration PR ДОЛЖЕН проверять применимые принципы и документировать обоснованные исключения.
- Продуктовые решения ДОЛЖНЫ фиксироваться в `knowledge/decisions.md`, а исходные свидетельства — в `knowledge/sources.md`.
- `AGENTS.md` остаётся единственным источником правил взаимодействия агента и ведения базы знаний. `CLAUDE.md` ДОЛЖЕН оставаться относительным symlink на него.
