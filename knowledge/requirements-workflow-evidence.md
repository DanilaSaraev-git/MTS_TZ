# Проверки на переходе от аналитики к разработке

Дата проверки источников: 2026-09-03. Статус: производный обзор официальной документации; инструменты в проекте не запускались. Область: текстовые требования, API, контракты данных и модели поведения. Применимость конкретных инструментов к нашим документам требует отдельной проверки. Это материал для продуктового анализа, не решение о составе или реализации продукта. Реестр: [S-09–S-16](sources.md).

## Различие объектов проверки

**Вывод обзора:** до реализации можно автоматически проверять саму спецификацию, примеры и формальную модель. Чтобы проверить соответствие будущей программы этим требованиям, нужна реализация либо её часть. Формально корректный документ не гарантирует, что описана нужная бизнесу система. Основания и ограничения ниже.

Для объяснения удобно разделять проверки формата, согласованности, моделей и бизнес-смысла. Это наша карта, а не общепринятая пирамида с установленными пропорциями. Чем больше требований выражено машинно проверяемыми правилами, тем больше доступно воспроизводимых проверок. Для свободного текста автоматический результат часто является кандидатом в замечание, а не доказанным дефектом.

## Проверки текстовых требований: QVscribe и Jama Connect Advisor

**Факты из источников.** QVscribe выявляет неполные предложения, выделяет термины и единицы измерения для проверки согласованности, находит сходные требования и показывает различия. Сходство помогает рецензенту искать дубли и возможные противоречия; это не доказательство логической непротиворечивости всего ТЗ. Источник: QRA, [QVscribe](https://qracorp.com/welcome-to-the-future-of-requirements-writing/), «Quality Analysis», «Unit & Term Consistency», «Similarity Analysis», S-09.

Jama Connect Advisor предлагает улучшения формулировок с опорой на INCOSE и EARS, а также генерирует тест-кейсы из требований для проверки и принятия инженерами. Источник: [Jama Connect Advisor](https://help.jamasoftware.com/ah/en/jama-connect-advisor-.html), вводный раздел и «Benefits of using Jama Connect Advisor», S-12.

**Граница проверки.** Упорядоченное предложение и сгенерированный тест-кейс не подтверждают правильность бизнес-правила. Независимой оценки точности этих продуктов, пригодности для русскоязычных документов и отраслевой применимости в этом исследовании нет.

**Синтез workflow:** черновик требований → автоматические замечания → разбор автором и экспертом → исправление → повторная проверка → согласование версии для разработки. Запуск при редактировании, по запросу или при смене статуса документа — варианты организации процесса; доступность конкретной интеграции проверять отдельно.

## Связи требований и анализ изменений

**Факты из источника.** Jama Connect хранит связи между потребностями, требованиями и тестами. Изменение вышестоящего элемента помечает связанные нижестоящие элементы как `suspect`, чтобы человек проверил последствия. Правила связей задают принятую методологию проекта. Источник: [Traceability from Requirements to Test](https://help.jamasoftware.com/ah/en/getting-to-know-jama-connect-features/traceability-from-requirements-to-test.html), «Benefits of establishing relationships», S-12.

**Граница проверки.** Связи с тест-кейсами можно установить до реализации, а результаты исполнения появятся позже. Наличие ссылки не доказывает смысловое покрытие требования тестом. Если исходные связи неполны, анализ изменений тоже ограничен.

**Синтез workflow:** связать требования, решения и сценарии проверки → изменить требование → получить список затронутых элементов → подтвердить актуальность или обновить их → согласовать новую версию.

## Контракты данных

**Факты из источников.** Data Contract CLI валидирует машиночитаемый контракт по JSON Schema стандарта ODCS. Контракт можно хранить в Git и проверять в CI. Отдельная команда `test` подключается к источнику и проверяет реальные данные на соответствие схеме и правилам качества. Источник: [What is Data Contract CLI?](https://docs.datacontract.com/), «Why data contracts?», «How it works», S-10.

Команда `breaking` сравнивает версии: например, удаление поля или ужесточение обязательности классифицируются как несовместимые изменения. Изменения первичного ключа и ограничения с неустановленным направлением получают предупреждение. Неизвестные изменения могут получить информационную классификацию, поэтому отсутствие ошибки не гарантирует смысловую совместимость. Источник: [Compare contract versions](https://docs.datacontract.com/compare-contract-versions), «Breaking changes», «Initial compatibility rules», S-10.

**Граница проверки.** Контракт и его версии проверяются до реализации нового потока. Проверка существующего источника тоже возможна заранее при наличии данных и доступа. Проверить фактическую корректность ещё не созданной витрины нельзя. Бизнес-смысл текстового описания не становится автоматически проверяемым от переноса в YAML.

**Синтез workflow:** согласовать поля и правила данных → описать контракт → проверить структуру и изменения → при наличии источника проверить его данные → согласовать контракт → реализовать поток → проверять результат по тому же контракту.

## Агентный процесс: GitHub Spec Kit

**Факты из источника.** В Spec Kit `clarify` запрашивает уточнения и сохраняет ответы в спецификации; `checklist` создаёт список критериев полноты, ясности и согласованности требований; `analyze` ищет расхождения между спецификацией, планом и задачами перед реализацией. Пользовательские чеклисты принадлежат рецензенту: их отметки означают принятие качества требований, а не готовность кода. Источник: [Agentic SDD](https://github.github.com/spec-kit/reference/agentic-sdd.html), одноимённые разделы команд, S-11.

**Граница проверки.** Это работа агента по проверке артефактов. Она не равнозначна детерминированному тесту бизнес-правил. Отсутствие замечаний не гарантирует отсутствие дефектов.

**Workflow по документации, сокращённо:** описание задачи → спецификация → уточнения → план → чеклист качества → задачи → анализ согласованности → исправления → реализация.

## BDD, Example Mapping и Cucumber

**Факты из источников.** Example Mapping проводят перед передачей истории в разработку: команда фиксирует правила, конкретные примеры и открытые вопросы. Это структурированное обсуждение людьми. Источник: Cucumber, [Example Mapping](https://cucumber.io/docs/bdd/example-mapping/), разделы «Example Mapping» и «How it works».

BDD разделяет работу на Discovery, Formulation и Automation: исследовать примеры, согласовать структурированное описание, затем связать каждый пример с системой как автотестом и реализовать поведение. Первый запуск такого теста может падать, поскольку поведение ещё не реализовано. Источник: Cucumber, [Behaviour-Driven Development](https://cucumber.io/docs/bdd/), разделы «Three practices», «Formulation: What it should do», «Automation: What it actually does».

Gherkin задаёт структуру сценариев `Given / When / Then`. Исполнение Cucumber требует сопоставить текст шагов с кодом `step definitions`; `Then` сравнивает наблюдаемый фактический результат с ожидаемым. Свободное описание Feature игнорируется при исполнении. Источник: Cucumber, [Gherkin Reference](https://cucumber.io/docs/gherkin/reference/), разделы «Feature», «Steps», «Then».

**Граница проверки.** До реализации доступны согласование примеров и проверка синтаксиса формата. Одно наличие `.feature` не означает ни автоматического поиска противоречий бизнес-правил, ни успешно пройденного приёмочного теста. Проверка поведения начинается после подключения исполняемых шагов к проверяемой системе или модели.

**Workflow по документации:** история → обсуждение правил, примеров и вопросов → согласованные сценарии → падающий исполняемый тест → реализация → повторные проверки и живая документация.

## API design-first: Spectral, Redocly CLI и Prism

**Факты из источников.** Spectral применяет набор правил к JSON/YAML, имеет готовые наборы для OpenAPI, AsyncAPI и Arazzo и поддерживает пользовательские правила. Доступны проверки шаблонов, параметров и наличия ключей. Официальный репозиторий указывает использование в редакторах, Git hooks и CI. Источник: Stoplight, [Spectral README](https://github.com/stoplightio/spectral), начальный список возможностей, «Usage», «Documentation», «Integrations».

Redocly CLI `lint` проверяет описания OpenAPI, AsyncAPI и Arazzo. Правила конфигурируются; результат указывает файл, строку и тип проблемы, поддерживает форматы для GitHub Actions и JUnit. В документированном примере обнаруживаются неверное поле `operationIds` и отсутствие `operationId`. Источник: Redocly, [lint](https://redocly.com/docs/cli/commands/lint), разделы «Introduction», «Extend configuration», «Codeframe», «GitHub Actions», «JUnit».

Prism создаёт mock HTTP API из OpenAPI до появления backend-кода; поддерживает проверку запросов. Отдельный режим validation proxy сравнивает трафик уже работающей реализации с описанием API. Источник: Stoplight, [Prism README](https://github.com/stoplightio/prism), разделы «Hosted Prism», «Self-hosted Prism», «Mocking», «Validation Proxy».

**Граница проверки.** Линтинг спецификации работает до кода. Mock позволяет попробовать согласованный интерфейс; успешный ответ mock не подтверждает корректность будущей бизнес-логики. Proxy и проверки фактических ответов требуют реализации. Отдельно нужна оценка полноты API относительно задачи потребителя.

**Синтез workflow:** изменение OpenAPI в pull request → автоматический lint по правилам команды → mock и просмотр интерфейса потребителями → согласование → разработка → проверки реализации относительно того же контракта. Это схема, составленная из возможностей инструментов, а не единый стандарт обязательного процесса.

## Pact: контрактные тесты на границе с реализацией

**Факты из источника.** Consumer-тест Pact регистрирует ожидаемые запрос и ответ в mock, вызывает код потребителя и проверяет, что тот правильно отправляет запрос и обрабатывает ответ. После успешных взаимодействий создаётся pact-файл. При provider verification запросы отправляются поставщику, а фактические ответы сравниваются с ожиданиями. Полная проверка контракта объединяет обе стороны без одновременного запуска двух сервисов. Pact рекомендует фокусировать контрактные тесты на сообщениях, а не на общей функциональности поставщика. Источник: Pact, [How Pact works](https://docs.pact.io/getting_started/how_pact_works), разделы «Consumer testing», «Provider verification», «Putting it all together», «Next steps».

**Граница проверки.** Ожидания можно сформулировать до реализации. Но стандартный consumer-driven workflow Pact уже проверяет код потребителя; provider verification требует проверяемого поставщика. Нельзя представлять Pact как полностью автоматическое ревью ТЗ, для которого вообще не нужен код. Контрактные тесты связывают согласование интеграции с последующим контролем реализации.

**Workflow по документации:** ожидаемое взаимодействие → тест кода потребителя с mock → pact-файл → верификация поставщика → интеграция результатов с CI.

## Формальные модели: TLA+ и TLC

**Факты из источников.** TLA+ описывает систему выше уровня программного кода. Модель задаёт состояния и переходы; свойства могут выражать неизменные ограничения и то, что событие в итоге произойдёт. Автор отдельно отмечает, что моделирование не предотвращает ошибки кодирования и любая модель описывает лишь выбранные аспекты системы. Источник: Leslie Lamport, [A High-Level View of TLA+](https://lamport.azurewebsites.net/tla/high-level-view.html), разделы «Introduction», «Models», «Modeling Above the Code Level», «Checking Properties».

TLC позволяет проверять deadlock, инварианты достижимых состояний и временные свойства. Для запуска задают модель, включая значения констант. Источник: TLA+ Toolbox, [Model Overview Page](https://tla.msr-inria.inria.fr/tlatoolbox/doc/model/overview-page.html), разделы «What is the behavior spec?», «What to check?», «What is the model?».

**Граница проверки.** Это настоящая автоматическая проверка формализованного проекта до написания продуктового кода. Результат относится к заданной модели, её параметрам, предположениям и свойствам. Он не доказывает ни бизнес-ценность требований, ни соответствие ещё не написанной реализации модели.

**Синтез workflow:** выделить критические правила и состояния → описать модель и проверяемые свойства → запустить TLC → исправить модель при нарушениях → согласовать → реализовать → отдельно проверить соответствие реализации.

| Подход | Что возможно до реализации | Что требует реализации или её части |
| --- | --- | --- |
| QVscribe / Jama Advisor | Замечания к формулировкам, терминологии, черновики тест-кейсов | Проверка фактического поведения по этим требованиям |
| Jama traceability | Связи артефактов и отметки о возможном влиянии изменений | Результаты выполнения тестов |
| Data Contract CLI | Валидация контракта и сравнение версий; проверка уже существующего источника при наличии доступа | Проверка фактического результата нового потока |
| GitHub Spec Kit | Уточнения, чеклисты, поиск расхождений спецификации, плана и задач | Проверка поведения реализованного продукта |
| Example Mapping / BDD | Обсуждение правил, примеров и вопросов; структурирование сценариев | Исполняемые приёмочные проверки фактического поведения |
| Spectral / Redocly lint | Проверка формата и правил описания API | Проверка соответствия фактических ответов спецификации |
| Prism mock | Генерация пробного API из описания; проверка запросов к mock | Validation proxy для реального API |
| Pact | Формулировка ожиданий участников интеграции | Consumer-тесты и provider verification |
| TLA+ / TLC | Проверка модели на заданные свойства | Отдельное подтверждение соответствия кода модели |

Это аналитическое сопоставление возможностей источников, а не опубликованная ими единая «пирамида требований». Эффект для конкретной команды и затраты на формализацию не измерены.

## Иллюстрация для ТЗ на данные

Синтетический пример, не фрагмент клиентского документа: «Каждый день рассчитывать выручку по клиенту».

| Проверка | Что она может дать | Что нужно дополнительно |
| --- | --- | --- |
| Структура документа | Указать отсутствие обязательного раздела с расписанием | Согласованный шаблон |
| Анализ формулировки | Спросить о часовом поясе, валюте, возвратах, поздних событиях | Подтверждение аналитика, какие вопросы существенны |
| Сверка контекста | Указать, что ожидаемое поле не найдено в доступной версии схемы источника | Актуальная схема и установленная связь с требованием |
| Контракт | Проверить формат схемы и формальные изменения относительно прошлой версии | Машиночитаемые ограничения и правила совместимости |
| Пример расчёта | Зафиксировать ожидаемый результат на небольшом наборе операций | Согласованные правила и ожидаемые значения; для исполнения — модель или код |

AI может предложить примеры, но ожидаемый результат должен иметь независимое основание: согласованное правило или подтверждение эксперта. Одинаковая ошибка в сгенерированных требованиях и тестах способна остаться незамеченной.

## Следствие для продуктового анализа

**Вывод обзора:** инструменты на этом переходе уже существуют. Наличие самого AI-ревью не следует считать доказанной новизной продукта. Возможный предмет сравнения для [H-03/H-04/H-13](hypotheses.md) — полезность адресных замечаний к ТЗ на данные, учёт контекста и доведение вопросов до согласованных правил.

**Предложение для будущей проверки, не принятое решение:** сравнить текущий процесс с цепочкой «ТЗ + доступный контекст → формальные проверки → кандидаты в смысловые замечания → подтверждение аналитиком → обновлённые правила и примеры → передача в разработку». Согласованные детерминированные проверки могут служить обязательным условием перехода; AI-замечания первоначально следует оценивать человеком. Численные критерии и запуск исследования не согласованы; использовать критерии существующих H-03/H-04/H-13 и [план проверки](discovery-plan.md).

Выполнено кабинетное исследование возможностей. Не выполнены установка инструментов, сравнение их качества, проверка русского языка, интервью о реальном использовании, пилот и измерение эффекта. Исследование не меняет статусы продуктовых гипотез.
