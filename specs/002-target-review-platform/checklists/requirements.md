# Specification Quality Checklist: Целевая платформа предварительного ревью ТЗ

**Purpose**: проверить полноту и качество спецификации до перехода к планированию

**Created**: 2026-09-04

**Feature**: [spec.md](../spec.md)

## Content Quality

- [x] Не зафиксированы конкретные языки, web-фреймворки, СУБД, очереди, хранилища или поставщики моделей.
- [x] Спецификация сосредоточена на пользовательской ценности, наблюдаемом поведении и границах продукта.
- [x] Термины согласованы с предметной областью проекта; новые понятия диалога определены отдельно.
- [x] Все обязательные разделы заполнены.

## Requirement Completeness

- [x] В спецификации нет маркеров `[NEEDS CLARIFICATION]`.
- [x] Функциональные требования проверяемы и не противоречат acceptance scenarios.
- [x] Release-критерии измеримы и отделены от неподтверждённых продуктовых порогов.
- [x] Success criteria не зависят от выбора конкретной технологии реализации.
- [x] Основные сценарии web, диалога, агентного/CLI-канала, совместной работы и self-hosted поставки имеют независимые проверки.
- [x] Ошибки документов, модели, конкурирующие изменения, policy-блокировки и configured-workspace namespace mismatch учтены в edge cases.
- [x] In scope и out of scope явно разделены.
- [x] Зависимости и допущения описаны, включая связь с PoC и отсутствие подтверждённых продуктовых порогов.

## Feature Readiness

- [x] Каждое функциональное требование покрывается пользовательским сценарием, edge case либо измеримым release-критерием.
- [x] User stories покрывают основной путь от документа до отчёта, диалога и решения человека.
- [x] Граница trusted deployment без auth, configured-workspace namespace, неизменяемость снимков и разделение результата модели и решения человека сформулированы как инварианты.
- [x] Диалог принимает один пользовательский ход за раз; фиксированный лимит не задан, решение принимает версия политики и раскрывает его через `can_send_message`/`blocked_reason`.
- [x] Техническая готовность не представлена как подтверждение полезности, спроса, экономии или переносимости.

## Notes

- Checklist подтверждает готовность спецификации к техническому планированию, а не подтверждение продуктовых гипотез.
- Численные пороги продуктового эффекта намеренно не выдуманы: перед экспериментом их нужно зафиксировать вместе с выборкой, сроком, исходным уровнем и ответственным в `product-knowledge/hypotheses-v2.md`.
- Конкретный web-стек относится к плану реализации или ADR и поэтому не включён в эту спецификацию.
- Перед параллельной реализацией машинные контракты ревью и диалога должны быть синхронизированы с этой спецификацией и заморожены общим контрактным изменением.
